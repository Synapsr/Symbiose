# Architecture

## Overview

```
 Mobile app (Expo)                      Server (one container)                  External
 ───────────────────                    ──────────────────────                  ────────
 Camera / text / barcode ── JSON ──►  Hono API ──► Claude (vision, structured) ─► Anthropic API
 Apple Health / Health Connect ─────►  SQLite (Drizzle) + /data/photos         ─► Open Food Facts
 React Query cache  ◄────────────────  deterministic nutrition math (shared)
```

- `packages/shared` holds the contract: zod schemas, types, nutrient metadata and every piece of nutrition math (targets, scaling, sanity checks, dates). Both the app and the server import it, so numbers are computed the same way everywhere.
- `apps/server` is a Hono app bundled into a single file with tsup. SQLite (better-sqlite3, WAL) and photos live in `DATA_DIR`. Migrations are generated by drizzle-kit and applied at start-up.
- `apps/mobile` is an Expo Router app. Server state goes through React Query; small client state (pending analyses, toasts, settings) lives in zustand stores.

## The AI proposes, code computes

The model never sets a number the user sees directly without a deterministic pass.

**Goals.** The user's own words go to `POST /api/goals/draft`. Claude returns a *strategy* (calorie mode and %, protein g/kg, fat share, daily rules such as "added sugar ≤ 25 g", focus nutrients, habits, coaching tone). The server clamps it (`services/goals.ts`): deficit ≤ 25 %, surplus ≤ 20 %, protein 0.8–2.4 g/kg, realistic bounds per rule. `computeTargets` then derives every target from the profile:

- BMR with Mifflin–St Jeor, maintenance = BMR × activity multiplier;
- with "adjust for activity" and watch data: maintenance = BMR × 1.2 + 80 % of measured active energy (wearables overestimate);
- deficits never go below BMR or a sex-specific floor (1200/1500 kcal);
- defaults follow WHO/EFSA (free sugars < 10 % of energy, saturated fat < 10 %, sodium < 2 g, fibre ≥ 25 g), then the plan's rules, then the user's manual overrides.

Without an API key, a keyword-based planner produces a reasonable plan so the app stays usable.

**Meals.** `POST /api/meals` with a photo and/or text runs one vision call with structured output (`ai/prompts.ts`, `ai/shared.ts`, then `ai/claude.ts` or `ai/openai.ts`). The prompt asks for edible grams and nutrients **per 100 g as served** from reference tables, with explicit rules for added vs total sugars and hidden fats. The server then:

1. sanitizes each item (`sanitizePer100g`): physical bounds, added sugar ⊂ sugar ⊂ carbs, saturated ⊂ fat, and an Atwater energy check that replaces a kcal value inconsistent with the macros by more than 35 %;
2. stores items per 100 g, so any portion change is an exact rescale;
3. computes goal-aware flags deterministically (share of each watched daily target used by the meal);
4. keeps the AI's verdict, one-sentence headline, up to two tips, and at most one clarification question when the answer would change the estimate materially.

Answering the question or typing a correction calls `/refine`, which re-runs the analysis with the previous items and the correction.

**Barcodes** go to Open Food Facts. When a product doesn't report added sugars, they are inferred from the ingredient list.

All Claude calls use structured outputs, adaptive thinking with per-task effort, and server-side refusal fallbacks (`fallbacks: "default"`).

Claude is the default and the reference. `AI_PROVIDER` can pick another provider (`ai/providers.ts`): they all go through one adapter on the OpenAI Chat Completions API (`ai/openai.ts`), with the same prompts, context, zod schemas and checks (`ai/shared.ts`), a strict JSON schema for structured answers, and the same error codes. A model that can't read photos answers photo meals with `ai_no_vision`; one that can't call tools gets a coach without proposals.

## Data model

| Table | Content |
| --- | --- |
| `users` | credentials (scrypt), profile and goal plan as JSON |
| `meals` | eaten-at (local time with offset), local date, items (JSON, per-100 g nutrients), photo id, AI insight |
| `photos` | ownership and mime of files in `DATA_DIR/photos` |
| `activity` | one row per day: steps, active/resting energy, weight, source |
| `cravings` | what, intensity, outcome, AI tip |
| `coach_messages` | conversation history and plan-change suggestions |
| `ai_cache` | cached reviews keyed by a hash of their inputs |

Dates are always the device's local calendar day (`localDate`), and timestamps keep their UTC offset, so "when do I eat sugar" is computed in the user's local hours.

## API

All routes except `/health`, `/` and `/api/info` require `Authorization: Bearer <token>`.

| Method | Path | |
| --- | --- | --- |
| POST | `/api/auth/register`, `/api/auth/login` | email + password → token |
| GET / PUT / DELETE | `/api/me`, `/api/me/profile`, `/api/me` | account; `GET /api/me/export` dumps everything |
| GET / POST / PUT | `/api/goals`, `/api/goals/draft`, `/api/goals` | current plan, preview a plan from text, save |
| POST | `/api/meals` | photo (base64 JPEG), text and/or items |
| GET / PATCH / DELETE | `/api/meals/:id` | edit portions, type, favorite… |
| POST | `/api/meals/:id/refine`, `/api/meals/:id/duplicate` | AI correction, "eat again" |
| GET | `/api/days/:date` | targets, totals, progress, meals, activity, cravings, streak |
| GET | `/api/foods/library`, `/api/foods/barcode/:code` | recents & favourites, Open Food Facts lookup |
| PUT | `/api/activity` | daily health data from the phone |
| POST / PATCH | `/api/cravings`, `/api/cravings/:id` | log a craving and get a tip, record the outcome |
| GET / POST | `/api/insights`, `/api/insights/review` | trends, top sources, by-hour distribution; AI review |
| GET / POST / DELETE | `/api/coach/messages` | coach conversation |
| GET | `/api/photos/:id` | meal photo (owner only) |

## Testing

- `packages/shared`: unit tests for energy, targets, sanitization and dates.
- `apps/server`: end-to-end API tests on an in-memory database with a fake AI and a fake Open Food Facts.
- `apps/mobile`: typecheck and lint (React Compiler rules), plus manual runs on web and devices.
